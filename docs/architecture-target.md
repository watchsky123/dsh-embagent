# 目标架构：AI 生成可运行初版（软硬件协同）

> **本文是目标设计，不是现状描述。** 刻意不参照任何现有实现，从"AI 如何生成一个
> 能被工程师接手、二次开发的嵌入式初版"这个目标反推。
>
> 写法上刻意把**设计决策、备选方案、开放问题**都摊开，便于研究修正。
> 每节末尾的「▷ 可质疑」标出我认为最可能需要你推翻的地方。

---

## 0. 一句话定位

> **生成"能跑、结构自洽、每个零件可归因"的初版；交付一份"哪里不确定"的合同；
> 让工程师接着改，而不是从头重做。**

成功标准不是"对不对"，而是：

| # | 判据 | 含义 |
|---|---|---|
| S1 | **可运行** | 固件真能编译、真能跑、串口真有输出 |
| S2 | **可归因** | 每个元件能回答"为什么在" |
| S3 | **可删除** | 删掉任一元件，有断言变红 |
| S4 | **可交接** | 未验证项聚合、排序、有归属 |
| S5 | **可增量** | 改一个需求，只重做受影响的部分 |

S3 是整个架构的支点，详见 §1。

---

## 1. 核心命题：**删除即失败**

### 1.1 观察

软件能"逐行生成"，不是因为模型聪明，而是因为它天然具备三条性质：

1. **局部依赖显式** —— `const x = f()` 之后，下一行能用 `x`
2. **效应可观测** —— 跑一下就知道 `x` 是什么
3. **删除即失败** —— 删掉这一行，下一行立刻报错

前两条硬件也有（引脚→网表→信号）。**唯独第三条硬件没有。**

### 1.2 推论

现在的硬件模型里，删掉一个 10k 上拉电阻，会发生什么？

- 几何检查：没事（少个元件不重叠）
- 边界检查：没事（少个元件不出界）
- 电气检查：没事（网表少了两个连接点）
- **没有任何东西变红**

这就是硬件难以"逐件生成"的根本原因：**没有执行器强制因果**。

### 1.3 架构支点

> **每个元件必须携带一条可执行断言；断言的失败条件包含"该元件不存在"。**

这条一旦成立，硬件就获得了软件的第三条性质。AI 可以像写代码一样逐件构建——
每加一个元件，就多一条能被验证的因果；每删一个元件，就有一个断言变红。

### 1.4 为什么不是"更强的仿真"

仿真回答的是"这样对不对"，断言回答的是"这个为什么必须存在"。

- 仿真强 → 能发现更多错误，但**发现不了"缺了什么"**（缺的东西不参与仿真）
- 断言强 → 能发现"少了什么"，这才是生成时的导航信号

两者互补，但**生成阶段的主导信号必须是断言**，因为搜索需要一个"缺什么"的梯度。

▷ **可质疑**：断言会不会退化成"把设计重写一遍"？
——风险真实。缓解：断言只声明**必要性与接口**，不声明实现细节（§4.3）。

## 2. 软件 vs 硬件的同构性（边界在哪）

你提出的类比是对的，但要标清哪一段成立、哪一段断掉。

| 维度 | 软件 | 硬件 | 是否同构 |
|---|---|---|---|
| 模块划分 | 函数/类/服务 | 功能单元/板 | ✅ 同构 |
| 模块接口 | 函数签名/API | 协议+电平+引脚 | ✅ 同构（更严格） |
| 依赖方向 | import 图 | 电源树 + 数据流 | ✅ 同构 |
| 逐行/逐件构建 | 是 | **可做到**（靠 §1 的断言） | ⚠️ 需机制 |
| 执行反馈 | 立即、免费 | 编译+数字仿真有；热/EMC 无 | ❌ **断点 1** |
| 错误代价 | 崩溃可重来 | **烧毁不可逆** | ❌ **断点 2** |
| 部署周期 | 秒 | 打板 2 周 | ❌ **断点 3** |

### 2.1 三个断点各自的应对

| 断点 | 不是"等模型变强"能解决的 | 架构上的应对 |
|---|---|---|
| 反馈缺失 | 热/EMC/机械无法运行 | **显式建模为 `unverifiable`**，不假装验证过（§6.4） |
| 不可逆 | 烧了不能重来 | 断言里加**极性/电平/绝对最大值**三类硬检查，优先级最高 |
| 周期长 | 物理时间 | 把"打板前必须确认的项"做成**阻断式闸门**（§8） |

▷ **可质疑**：断点 2 是不是被低估了？
一次极性接反可能烧掉整板，而 AI 生成的初版最可能的错误恰恰是这类。
——所以我建议**硬检查优先于一切优化**，宁可保守（§4.4）。

## 3. 分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│  L5  交接层       handoff.md · assertions.md · 阻断闸门            │
├──────────────────────────────────────────────────────────────────┤
│  L4  验证层       符号 → 约束 → 几何 → 电气DC → 时序 → 仿真 → SPICE │
│                   （阶梯，便宜的先跑，硬失败可截断）                 │
├──────────────────────────────────────────────────────────────────┤
│  L3  断言层       claim.*：每个元件/连接/单元的可执行因果            │
├──────────────────────────────────────────────────────────────────┤
│  L2  连接层       net（板内）· link（板间）                        │
├──────────────────────────────────────────────────────────────────┤
│  L1  器件层       part：型号 + 尺寸 + 引脚 + 归因                   │
├──────────────────────────────────────────────────────────────────┤
│  L0.5 单元层      unit：功能块 + 板分配 + 单元间接口                │
├──────────────────────────────────────────────────────────────────┤
│  L0  需求层       requirement：数字 + 约束 + 验收判据               │
└──────────────────────────────────────────────────────────────────┘
              ▲                                    │
              │        失败回灌（收窄约束）          │
              └────────────────────────────────────┘
```

**关键**：L0 到 L5 是**数据层**。生成器是横跨它们的一个**搜索循环**（§5），不是某一层。

## 4. 数据模型

### 4.1 L0 需求（`requirement.yaml`）

需求必须是**可判定的数字**。形容词（"轻便"、"流畅"）在进入模型前必须转成数字或明确标 `assumed`。

```yaml
schema: hw.requirement/1
id: drone-v1
title: 示例-单板四旋翼

functional:                     # 定性，用于角色推导
  - 四旋翼垂直起降
  - 遥控 + 图传
  - GPS 定位 + 光流定高 + 前向避障

numeric:                        # ★ 定量，用于断言与协同验证
  flight:
    time_min: 12
    mtow_g: 1200
  link:
    bandwidth_mbps: 8
    latency_ms_max: 300
  sensing:
    detect_distance_mm: 3000
    min_target_mm: 150
    pointing_accuracy_deg: 1.0
  power:
    rail_5v_rated_a: 2.0
    rail_5v_min_v: 4.8
    rail_3v3_rated_a: 0.5

constraints:                    # 硬约束，不满足即不可行
  board_area_mm2: [96.1, 85.9]
  layers: 4
  cost_usd_max: 120
  connector_series: [GH1.25, XT30]
  package_pitch_mm_min: 0.5

interfaces:                     # ★ 板间约定，生成 L2 的输入
  - id: IF-01
    from: pilot
    to: front
    protocol: uart
    baud: 921600
    level_v: 3.3
    direction: bidirectional
    payload: obstacle_distances

acceptance:                     # ★ 什么时候算"初版可用"
  - all.parts.have_justification
  - all.claims.evaluable
  - unverifiable.items.have_owner
  - hard_checks.all_pass
```

**纪律**：`numeric` 里每个数字都要有 `source`：
`datasheet | requirement | assumed | measured`。`assumed` 的必须进 `handoff.md`。

▷ **可质疑**：需求里放 `interfaces` 是否越界？
——这是设计决策：我认为**板间协议应该在需求层定**，因为它是系统分解的产物，
而不是器件选择的结果。备选方案是在 L0.5 单元层再定（§11 开放问题 4）。

### 4.2 L0.5 功能单元（`units.yaml`）

单元是**逻辑分组**，一个单元对应一块板或一块板上的一个功能域。

```yaml
schema: hw.units/1
units:
  - id: pilot
    role: 主控与决策
    board_hint: 96x86mm, 4-layer
    owns_roles: [mcu, radio, power_in, imu]
    provides_to: [front, bottom, gps]
    justification:
      requirement: [REQ-CTRL-01]
      why: 姿态解算与串级 PID 需要最高算力，且是所有链路的汇聚点

  - id: front
    board_hint: 30x30mm
    owns_roles: [avoidance_radar]
    justification:
      requirement: [REQ-AVOID-01]
      why: 雷达需正前方无遮挡，放在主板上会被机臂挡住

links:                          # 从 requirement.interfaces 落成具体端点
  - id: L-IF01
    a: {unit: front, peripheral: USART2, pins: [PA2, PA3]}
    b: {unit: pilot, peripheral: USART3, pins: [PD8, PD9]}
    protocol: uart
    params: {baud: 921600, level_v: 3.3}
```

**为什么单独一层**：这是你要求的"硬件模块设计"所在。现在的痛点是跨板关系
无处表达（net 只有 `{net, pins}`，没有 board 维度）。这一层把它变成一等公民。

### 4.3 L1 器件（`parts`）

```yaml
- ref: U3
  kind: gps_module
  model: BN-220
  unit: pilot
  size_mm: {w: 22, h: 22, d: 6}
  size_source: datasheet
  pins:
    - {name: TX, net: GPS_TX}
    - {name: RX, net: GPS_RX}
    - {name: VCC, net: 3V3}
    - {name: GND, net: GND}

  # ★ 归因：为什么这个元件在这里
  justification:
    requirement: [REQ-NAV-02]
    why: 光流只能相对定位，返航与定点需要绝对坐标
    effect_if_removed: 失去绝对位置，返航模式失效
    alternatives: [BN-880, M10-5883]     # 便于二次开发换料
    cost_driver: 决定 BOM 中导航部分成本

  # ★ 断言引用（不是内联，见 L3）
  claims: [claim.nav.absolute_position]
```

**归因的粒度原则**（这是要重点讨论的）：

| 元件类型 | 归因粒度 | 理由 |
|---|---|---|
| 功能件（MCU/GPS/雷达/相机） | **逐个** | 每个都是架构决策 |
| 无源件（电阻/电容） | **按功能组** | 单个 0402 电容不需要独立理由，但"这组去耦电容"需要 |
| 连接器 | **逐个** | 决定外壳与线束 |

▷ **可质疑**：这就是 §11 开放问题 1。141 个元件逐个写归因成本极高，
按组写又可能丢失信息。我倾向"功能组 + 组内清单"，但需要你判断。

### 4.4 L3 断言（`claims`）—— 架构支点

```yaml
- id: claim.nav.absolute_position
  type: capability
  scope: {unit: pilot}
  intent: 系统能给出绝对位置

  # 依赖：断言存在的前提
  requires:
    - part.U3
    - link.U3.UART1->U1.USART2

  # 可执行检查
  check:
    kind: composite
    all_of:
      - kind: presence
        expr: exists(part(ref=U3).provides.position_fix)
      - kind: protocol
        expr: link(U3.UART1, U1.USART2).protocol == "uart"
      - kind: numeric
        expr: link(U3.UART1, U1.USART2).params.baud >= 9600

  # 失败时给出什么
  on_fail:
    message: 绝对定位链路不完整
    narrow:                                 # ★ 回灌给搜索的约束
      - {action: add_part, role: gps, unit: pilot}
      - {action: add_link, from: "*.UART", to: "pilot.USART*"}
```

**三类断言的优先级**（对应 §2.1 断点 2：不可逆）：

| 优先级 | 类型 | 例子 | 失败后果 |
|---|---|---|---|
| **P0 硬** | 极性/绝对最大值/短路 | 5V 灌 3.3V 引脚、电源反接 | **烧板** |
| **P1 硬** | 电平/协议兼容 | 3.3V UART 接 5V 外设 | 通信失败或损伤 |
| P2 | 能力/数值 | 电流预算、波特率可达 | 功能不达预期 |
| P3 | 结构/几何 | 重叠、出界、限高 | 装不上 |

**P0/P1 失败必须阻断所有后续优化**——因为下游结论建立在"板还活着"的假设上。

### 4.5 L2 连接（`nets` + `links`）

两套，**不要合并**：

```yaml
nets:                            # 板内铜连接
  - {net: GPS_TX, pins: [{ref: U3, pin: TX}, {ref: U1, pin: PA10}]}

links:                           # 板间线束
  - id: L-IF01
    a: {unit: front, peripheral: USART2, pins: [PA2, PA3]}
    b: {unit: pilot, peripheral: USART3, pins: [PD8, PD9]}
    protocol: uart
    params: {baud: 921600, level_v: 3.3}
    source: ioc                  # ioc | declared | inferred
    evidence: "F401-Front.ioc: PA2=USART2_TX"
```

**为什么不合并**：板内是铜（P CB 工艺），板间是线束（连接器 + 线）。
它们的物理约束完全不同（板内有布线层数限制，板间有线长/屏蔽/插拔寿命）。
合并会丢掉这个区别。

**端点用 `unit.peripheral` 而不是 pin**：一条 UART 链路已经是两个引脚了，
在链路层再说引脚是重复。这个抽象让"协议一致性"能独立检查。

## 5. 生成器：四段式 + 闭环搜索

### 5.1 四段

```
需求 ──①──→ 单元 ──②──→ 器件 ──③──→ 连接 ──④──→ 断言
  ↑                                                  │
  └────────── 失败回灌（收窄约束，只重做受影响段）←────┘
```

| 段 | 输入 | 输出 | 失败时回退到 |
|---|---|---|---|
| ① 需求→单元 | `requirement.yaml` | `units.yaml` | 需求（要人改） |
| ② 单元→器件 | 单元规格 + 知识图谱 | `parts` | ①（重分单元） |
| ③ 器件→连接 | 器件引脚 + `interfaces` | `nets` + `links` | ②（换器件） |
| ④ →断言 | 全部 | `claims` | 无（断言由规则生成） |

**每段的产物都是可独立审阅的文件**，不是内存中的中间态。
这是为了你能在任意一段停下来看、改、再继续。

### 5.2 闭环

```python
def generate(req):
    units = decompose(req)                       # ①
    for attempt in range(MAX):
        parts = pick_parts(units, kg, constraints)   # ②
        links = wire(parts, req.interfaces)          # ③
        claims = derive_claims(parts, units, links)  # ④
        result = verify(claims, parts, units, links) # L4 阶梯

        if result.hard_fail:              # P0/P1
            constraints += result.narrow
            continue                      # 只重做 ②
        if result.soft_fail:
            units = re_decompose(units, result.narrow)   # 回 ①
            continue
        if result.unknown:                # not_verified
            break                         # 允许成功，但记入交接
        break
    return artifacts(units, parts, links, claims, result)
```

**三条关键规则**：

1. **硬失败只回退到 ②，不推翻整个设计**——换料而不是重做架构。
2. **软失败才回退到 ①**——说明分解本身有问题。
3. **`unknown` 不算失败**——允许带着未验证项交付，但必须进交接清单。

▷ **可质疑**：这个循环会不会不收敛？
——需要 `MAX` 上限 + 每次回灌必须**严格收窄**约束（单调性），否则会震荡。
这是 §11 开放问题 3。

## 6. 验证阶梯

### 6.1 阶梯

| 级 | 名称 | 成本 | 能发现 | 不能发现 |
|---|---|---|---|---|
| V0 | 符号 | µs | 引用不存在、类型错 | 一切物理 |
| V1 | 约束 | ms | 电平/极性/电流/波特率/面积 | 几何、时序 |
| V2 | 几何 | ms | 重叠/出界/限高/keepout | 电气 |
| V3 | 电气 DC | ms | 轨跌、稳压器结温、线降 | 瞬态、纹波 |
| V4 | 时序/协议 | 100ms | 波特率可达、建立保持 | 模拟行为 |
| V5 | 数字仿真 | s | **固件真执行 + 串口** | 模拟电路 |
| V6 | SPICE 瞬态 | min | 纹波、电感、环路 | 热、EMC |
| **V7** | **热/EMC/机械/工艺** | — | — | **全部（不可仿真）** |

### 6.2 执行规则

```
按 V0→V6 顺序跑；
某级 P0/P1 硬失败 → 截断，不跑后续（下游结论无意义）；
某级软失败 → 继续跑完，但结果标记 degraded；
V7 永远不跑，永远标 unverifiable。
```

**截断规则很重要**：现在的做法是全量跑，但"电源会烧"的情况下继续算时序是浪费。

### 6.3 每级的输出格式统一

```yaml
- id: V3.rail_5v
  level: V3
  status: pass | fail | unknown
  measured: {v_at_load: 4.874, load_a: 1.4}
  limit: {min_v: 4.8}
  # ★ 关键：unknown 必须与 pass 分开
  unknown_reason: null
```

**`unknown` 绝不等于 `pass`**。这条是整个架构的诚信底线。

### 6.4 V7：不可仿真项的显式建模

```yaml
unverifiable:
  - id: U-01
    what: 5V 轨在四旋翼满推时的瞬态跌落
    why_not: 需要电机电流波形 + 电池内阻温度特性，DC 模型不含
    risk: high
    owner: 硬件工程师
    how_to_check: 实测示波器 + 电子负载阶跃
  - id: U-02
    what: 图传天线与 GPS 天线的耦合
    why_not: 需 EMC 近场扫描
    risk: medium
    owner: 射频工程师
    how_to_check: 暗室或近场探头
```

**这张表就是交接合同的核心。** 它比"我验证了 8 项"有价值得多，
因为它说清了"我没验证什么、为什么、谁来验、怎么验"。

## 7. 知识图谱层（候选生成的基础）

### 7.1 为什么需要

从需求到器件不是"选一个型号"，而是在 **10²⁰ 量级**的组合里找可行解
（PCBgen 论文给的量级）。没有结构化知识，模型只能靠记忆，必然遗漏。

### 7.2 图的结构

```
节点：
  Part      —— 具体型号，带 datasheet 事实
  Capability—— 抽象能力（uart@3.3V, current<50mA, position_fix）
  Requirement—— 需求项
  Unit      —— 功能单元
  Protocol  —— 协议族（uart/i2c/spi/can）

边：
  Part --provides--> Capability
  Part --requires--> Capability
  Requirement --needs--> Capability
  Unit --owns--> Capability
  Protocol --constrains--> (level, baud, pins)
```

### 7.3 查询接口

候选生成靠查询，不靠模型记忆：

```
?part --provides--> position_fix
      --requires--> power(3.3V, <50mA)
      --protocol--> uart
      --footprint--> area < 500mm²
      --stock--> available
```

**这才是把 10²⁰ 砍到 10³ 的地方**——纯符号，毫秒级。

### 7.4 知识来源与可信度

| 来源 | 可信度 | 用途 |
|---|---|---|
| datasheet 人工录入 | `datasheet` | 可参与硬检查 |
| 厂商 API（LCSC/Mouser） | `vendor` | 可用于选型，不可用于硬检查 |
| 模型推断 | `inferred` | **永不参与硬检查**，只作草稿 |
| 实测 | `measured` | 最高 |

**`inferred` 永不等于 verified**——这条必须写进不变量（§9）。

## 8. 交接层

### 8.1 三份产物

| 文件 | 回答 | 读者 |
|---|---|---|
| `design.json` | **有什么** | 工具链 |
| `assertions.md` | **每个东西为什么在、删了会怎样** | 工程师 |
| `handoff.md` | **哪里不确定、谁去验、怎么验** | 工程师 + 项目经理 |

### 8.4 阻断闸门

不是所有项目都要过闸门。分两档：

| 档 | 允许的未知 | 适用 |
|---|---|---|
| **打样档** | P0/P1 必须全过；P2/P3 可 `unknown` | 出 Gerber |
| **评审档** | 任意 `unknown` 可交付，只要进交接 | 内部讨论 |

▷ **可质疑**：闸门会不会太严导致永远出不来？
——需要实践校准。建议先给"评审档"默认，打样档手动切换。

## 9. 不变量（可证伪的设计承诺）

这七条是架构的"宪法"，任何实现都不得违反：

| # | 不变量 | 违反的后果 |
|---|---|---|
| I1 | **`unknown` ≠ `pass`** | 用户以为验过了 |
| I2 | **`inferred` 永不参与硬检查** | 假数据通过真检查 |
| I3 | **每个元件必须有 `justification`** | 生成物无法二次开发 |
| I4 | **每条断言必须可独立复现** | 结论不可信 |
| I5 | **用默认值的结论必须计入 `unknown`** | 假验证 |
| I6 | **P0/P1 失败必须截断下游** | 基于错误前提继续推理 |
| I7 | **不可仿真项必须显式建模** | 黑箱被当成"没问题" |

▷ **可质疑**：I3 会不会让生成变慢/成本过高？
——这是 §1 的代价。我认为值得，但需要 §11 开放问题 1 的答案。

## 11. 开放问题（最需要你判断的）

### Q1 归因粒度：元件级还是功能组级？

- **元件级**：信息完整，但 141 个元件逐个写成本高，AI 可能写出空洞的套话
- **功能组级**："GPS 复位上拉组" 一条，组内 3 个元件共享，成本 1/10，但换料时丢失上下文
- **我的倾向**：功能组 + 组内清单，且**功能件（MCU/传感器/连接器）必须逐个**

### Q2 断言的表达力边界

哪些用声明式（可判定），哪些必须走仿真？

- 存在性、参数范围、协议匹配 → 声明式，毫秒级
- 波特率可达 → 声明式（时钟/分频计算）
- 纹波、环路稳定性 → **必须 SPICE**
- 时序建立保持 → 需要器件时序表

**分界线在哪，决定了断言层能不能"便宜地"指导搜索。** 如果太多断言需要仿真，
搜索就退化成"每次试错都跑 SPICE"，失去速度优势。

### Q3 搜索的收敛性

§5.2 的循环需要**单调收窄**才能保证终止。但硬件设计里，
"换一个更便宜的器件"可能引入新约束（封装变大 → 面积不够），
这时约束不是单调的。

**可能需要**：约束分层（硬约束单调，软约束可放松）+ 分支限界，
而不是简单循环。这块我没有可靠答案。

### Q4 板分配是搜索还是人给？

- **人给**：可控，但 AI 不能"从 0"（要人先定几块板）
- **AI 搜**：能真正从 0，但组合爆炸（7 个角色分到 4 块的方案数不小）
- **折中**：AI 给 2–3 个候选分配，人选一个，再往下

**我倾向折中**，因为这恰好是"初步项目 + 人工确认"的形态。

### Q5 不可仿真项如何在交接里表达才不误导？

`unverifiable` 列表容易被读成"已知风险"（其实是"未知风险"）。
可能需要三级：`known_risk | unknown_risk | assumed`。

### Q6 控制律要不要进这个模型？

我的判断是**不进**：四旋翼的姿态融合、串级 PID、失效保护是算法，
不是电路。硬塞进来会让模型边界模糊。

但**接口要进**：飞控需要什么输入（IMU 频率、GPS 更新率、遥控延迟），
这些是 `numeric` 需求，能被断言检查。

### Q7 二次开发时 AI 如何理解人类的修改？

工程师改了 `design.json` 之后，AI 下次怎么知道"这是人的决定，别再改回去"？

可能需要：修改标记（`source: human`）+ 断言降级（人改过的地方，断言变成"提醒"而不是"阻断"）。
这块完全没有设计。

## 12. 与"一次做对"的区别（回应你的定位）

| | 一次做对 | 本文档的定位 |
|---|---|---|
| 目标 | 可用产品 | **可运行的初版** |
| 失败标准 | 有 bug | **不可归因 / 不可交接** |
| AI 的角色 | 替代工程师 | **替代"从空白开始"这一步** |
| 人的角色 | 验收 | **验证 + 二次开发** |
| 成功的度量 | Pass@1 | **`unverifiable` 有归属 + 每条可删可查** |

**所以这个架构的"完成度"不是"设计对不对"，而是"交接合不合格"。**
`handoff.md` 的质量，比 `design.json` 的正确性更能决定项目成败。

## 13. 最小可行切片（如果只做一件事）

如果只能实现架构的一部分，我建议：

> **元件级 `justification` + 一条"删除即失败"的断言机制。**

理由：其余各层（知识图谱、约束预筛、SPICE 闭环）都是"让生成更准"，
而这一条是"让生成变得可能"。没有它，AI 的产物永远是一堆无法二次开发的零件。

验证方式很朴素：

```bash
hw_assert --remove R12       # 删掉一个上拉电阻
# 期望：claim.gps.reset_stable 变红，并说明"RESET 网络失去默认电平"
```

如果这条跑不通，后面所有层都是空中楼阁。
